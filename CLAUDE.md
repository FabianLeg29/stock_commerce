# Suivi Stock — Production & Commerce (SAS La Légumière)

Application web de suivi du stock quotidien (saisie du stock du soir par la production, achats/ventes/prix par le commerce), pour l'entreprise **la légumière**. Construite sur le même modèle que l'application sœur `Plan_stockage_allium` (paloxs échalotes/oignons), mais avec son propre projet Firebase et son propre dépôt GitHub. Ce fichier résume ce qui a été construit pour qu'une session Claude (ou un autre développeur) reprenne le contexte rapidement.

## Vue d'ensemble

- **Un seul fichier** `index.html` — HTML + CSS + JavaScript vanilla (pas de framework, pas de build). Tout le JS est dans une balise `<script>` en IIFE.
- **Multi-utilisateur en temps réel** via Firebase : Authentication (email/mot de passe) + Firestore. Sans Firebase, pas de partage de données entre les tablettes production et l'ordinateur commerce — contrainte assumée, comme pour l'app paloxs.
- **Hébergement** : GitHub Pages, dépôt dédié (`Suivi_Stock_Legumiere` ou équivalent), séparé du dépôt paloxs.
- **Projet Firebase** : séparé du projet paloxs (`plan-de-stockage-alliums`) — comptes et données indépendants, par choix explicite (voir historique de conversation : l'utilisateur a préféré isoler les deux outils plutôt que mutualiser les comptes).

## Différence de modèle de données par rapport à paloxs

L'app paloxs stocke tout dans **un seul document Firestore** (`planStockage/main`), pertinent pour un état "photo à l'instant T" (plan de cellules). Ici, les données sont un **flux quotidien qui grossit sans fin** (une entrée par produit et par jour, tous les jours) — un document unique grossirait indéfiniment et finirait par dépasser les limites Firestore. Le modèle est donc volontairement différent :

```
Firestore
├── produits/{produitId}     { nom, famille, variete, origine, conditionnement, suremballage, actif, prixAchatDefaut, prixAchatUnite, ordre }
├── referentiels/main        { familles: [...], varietes: [{ nom, famille }, ...], origines: [...], conditionnements: [...], suremballages: [...], fournisseurs: [...] }  ← listes gérées depuis l'onglet Produits (admin + commerce)
├── parametres/operateurs    { liste: [...] }   ← opérateurs de stock du soir, gérés depuis l'onglet Paramètres (admin uniquement)
├── parametres/historique    { joursConservationStockSoir: nombre|null }   ← durée de rétention de saisieStock/brouillonsStockSoir, gérée depuis Paramètres (admin uniquement)
├── dernierStock/main        { [nomProduit]: { valeur, date } }   ← cache du dernier stock connu (alimenté par la validation commerce, pas directement par la production)
├── saisieStock/{date__slug} { date, produit, stockHaut, stockHautOperateur, stockHautHeure, stockBas, stockBasOperateur, stockBasHeure, stockSoir, importe, horodatage, responsable }
├── brouillonsStockSoir/{date__cote__slugOperateur} { date, cote, operateur, heure, valeurs: { [nomProduit]: valeurTexte }, miseAJour }  ← brouillon persisté d'une session de comptage en cours (avant "Terminer et enregistrer")
├── commerce/{date__slug__commercial} { date, produit, commercial, ventes, reservations, horodatage, responsable }
├── achats/{autoId}          { date, dateLivraisonPrevue, fournisseur, responsable, horodatage,
│                              lignes: [ { produit, quantite, prixAchat, heureDepart, transportType, transporteurNom } ] }
├── transactions/{autoId}    { date, type, produit, valeur, responsable, horodatage }   ← journal (Historique)
├── clotures/{date}          { date, heure, responsable }   ← seuil de "clôture de journée" (Commerce), ne supprime aucun achat/vente
└── users/{uid}              { email, role }
```

Points importants :
- **`produits/{produitId}`** : un document par produit (`produitId` = `slugify(nom)`). Créé/modifié/supprimé par l'admin **et** le rôle `commerce` depuis l'onglet Produits (gestion complète) ; le rôle `production` ne peut modifier que le champ `actif` (réactivation depuis l'onglet Production). Chargé en entier au démarrage (`onSnapshot` sur la collection, triée côté client par `ordre`) — volume faible, pas de pagination nécessaire. Le produit ne porte plus de champ `reservations` persistant (voir `commerce` ci-dessous — les réservations sont désormais quotidiennes, comme les ventes).
- **`referentiels/main`** : un seul document. `familles`, `origines`, `conditionnements` et `suremballages` sont des tableaux de chaînes ; `varietes` est un tableau d'objets `{ nom, famille }` — **chaque variété est rattachée à une famille**, pour que le menu Variété de la fiche produit ne propose que les variétés de la famille choisie (cascading select). Une variété créée sous un schéma antérieur à ce lien (chaîne isolée, sans `famille`) est normalisée à la lecture en `{ nom, famille: '' }` plutôt que de planter l'affichage — elle n'apparaît alors dans aucun filtre par famille tant qu'elle n'est pas recréée sous une famille. Géré par l'admin **et** le rôle `commerce` (même droits que sur `produits`), depuis une section dédiée de l'onglet **Produits**, avec ajout/retrait via `arrayUnion`/`arrayRemove` (ou remplacement direct du tableau `varietes` pour la suppression en cascade des variétés d'une famille supprimée). Les listes déroulantes de la fiche produit lisent l'union de ces valeurs et de celles déjà utilisées sur des produits existants, pour ne rien perdre des produits créés avant l'introduction de cette collection.
- **`dernierStock/main`** : cache dénormalisé, mis à jour **uniquement par le rôle commerce** lors de la validation du stock du soir (onglet Commerce > « Stock du soir à valider »), pour que l'onglet Commerce affiche le "dernier stock connu" sans avoir à faire une requête historique par produit. La production ne l'écrit plus directement — ses saisies transitent d'abord par `saisieStock` (champ `importe: false`) avant d'être validées.
- **`saisieStock`** : un document par produit et par jour (id = `${date}__${slug(produit)}`), écrit par la production. `stockHaut` et `stockBas` (deux niveaux de comptage physique) portent chacun leur propre attribution — `stockHautOperateur`/`stockHautHeure` et `stockBasOperateur`/`stockBasHeure` — car un opérateur peut réaliser le Haut et un autre le Bas, à des moments différents ; `stockSoir` est leur somme, calculée automatiquement au moment de l'enregistrement (jamais recalculée côté client à l'affichage). Le rôle commerce peut uniquement faire passer `importe` à `true` (règle Firestore restreinte à ce seul champ) lors de la validation, ce qui répercute alors la valeur dans `dernierStock`. Interrogée pour l'affichage du jour avec `where('date','==', aujourdhui)`, et pour la file d'attente de validation avec `where('importe','==', false)` — deux filtres simples, aucun index composé nécessaire. Un bouton **« Exporter le stock du soir (.xlsx) »** dans l'onglet Stock du soir génère un export SheetJS (Famille/Produit/Haut/Bas/Total) du jour, indépendant de la validation commerce — un enregistrement que la production peut garder de ce qu'elle a saisi le soir. Un bouton **« Exporter le stock du soir (.pdf) »** (`exporterStockSoirPDF()`) fait de même via la boîte d'impression du navigateur (même principe que l'export PDF des achats, zone partagée `#zoneImpression`).
- **`parametres/historique`** : `{ joursConservationStockSoir: nombre|null }`, un seul champ, géré par l'admin depuis l'onglet **Paramètres** (`enregistrerJoursConservation()`). `null`/vide = rétention illimitée (comportement par défaut, aucune suppression). Si une valeur est définie, une purge côté client (`lancerPurgeHistoriqueSiBesoin()`, l'app n'a pas de backend/Cloud Function) supprime au chargement — une fois par session, uniquement pour un compte `admin` (seul rôle autorisé à supprimer `saisieStock` par les règles Firestore) — les documents `saisieStock` et `brouillonsStockSoir` dont `date` est antérieure au seuil (`where('date', '<', seuil)`, requête simple, aucun index composé). **La purge ne se déclenche jamais tant qu'aucun admin ne s'est connecté** depuis que la limite a été fixée (pas de tâche planifiée serveur) — pour une purge fiable, un compte admin doit se connecter régulièrement.
- **`brouillonsStockSoir`** : un document par jour + côté + opérateur (id = `${date}__${cote}__${slug(operateur)}`), écrit/effacé par la production (mêmes droits que `saisieStock`). Persiste le contenu de `saisieSessionEnCours` (`valeurs: { [nomProduit]: valeurTexte }`) pendant qu'une session de comptage est en cours, avec auto-sauvegarde débouncée (800 ms) à chaque saisie — la session survit donc à la fermeture de l'onglet/du navigateur, et **plusieurs opérateurs peuvent avoir chacun leur propre session "en cours" en parallèle** (même pour le même côté), affichées en cartes « Stock en cours » au-dessus du formulaire « Démarrer un stock du soir », avec un bouton « Reprendre le stock en cours » par session (`reprendreStockEnCours()`). Le document est supprimé au clic sur « Terminer et enregistrer » (succès) ou « Annuler ». **Limite connue** : si deux opérateurs comptent en parallèle le **même côté** en se répartissant les produits, celui qui clique sur « Terminer » en premier écrit 0 pour les produits que l'autre n'a pas encore saisis (voir le comportement de mise à zéro de `saisieStock` ci-dessous) — ce mécanisme est pensé pour reprendre une session interrompue ou pour que deux personnes comptent indépendamment (l'une prenant le relais de l'autre), pas pour un dénombrement scindé produit par produit entre deux personnes sur la même session.
- **`parametres/operateurs`** : `{ liste: [...] }`, un seul document, tableau de chaînes — les personnes physiques réalisant les contrôles de stock du soir, distinctes des comptes de connexion Firebase (un même compte/tablette peut être partagé par plusieurs opérateurs). Géré exclusivement par l'admin depuis l'onglet **Paramètres**, lecture ouverte à tous les rôles connectés (le choix d'un opérateur se fait sur l'écran de démarrage de l'onglet Stock du soir, ajout/retrait via `arrayUnion`/`arrayRemove`, même schéma d'interface que les cartes de Listes de référence).
- **`commerce`** : une collection à écriture continue, un document par produit **et par commercial** et par jour (id = `${date}__${slug(produit)}__${slug(emailCommercial)}`), interrogée avec `where('date','==', aujourdhui)`. Porte `ventes` **et** `reservations` — les deux sont désormais quotidiennes (réinitialisées chaque jour, comme les ventes), saisies individuellement par chaque commercial pour ses propres ventes/réservations du jour, et sommées côté client pour obtenir les totaux "Global". `achats` et `prixAchat` du jour ne sont pas dans ce document et vivent dans la collection `achats`.
- **`achats/{autoId}`** : un document par **livraison** (pas par produit) — un fournisseur, une date (jour de saisie de l'achat), une **date de livraison prévue** optionnelle (`dateLivraisonPrevue`, nullable — distincte de `date` : le jour où la marchandise doit arriver, potentiellement différent du jour de commande), et une ou plusieurs `lignes` (une par produit reçu dans cette livraison), chaque ligne portant sa propre quantité, prix d'achat, heure de départ et transport (`transportType: 'ramasse' | 'transporteur'`, `transporteurNom` si transporteur) — pensé ainsi car une même livraison peut se scinder entre plusieurs moyens de transport selon les lignes. Modifiable/supprimable par le rôle `commerce` (pas réservé à l'admin, contrairement aux produits). L'onglet **Commerce** interroge cette collection avec `where('date','==', aujourdhui)` et additionne les `quantite` par produit pour calculer le stock réel du jour — aucun index composé nécessaire (filtre sur un seul champ). L'onglet **Achats** charge en plus un historique complet (`orderBy('horodatage','desc').limit(200)`, chargement paresseux comme `transactions`) pour le récapitulatif ; comme cet historique est plafonné aux 200 achats les plus récents, une section **« Consulter les achats d'une date »** (`consulterAchatsDate()`, requête ponctuelle `achats.where('date','==', dateChoisie)`, même principe que « Consulter un stock antérieur ») permet de retrouver un achat plus ancien que cette limite.
- **`transactions`** : journal des actions (comme l'Historique de paloxs), avec export CSV (point-virgule, BOM UTF-8 — même convention que le CSV de paloxs), suppression réservée à l'admin.

## Rôles et droits (5 niveaux)

Stockés dans Firestore, collection `users`, un document par compte (`id` = UID Firebase Auth), champs `email` + `role`.

- **`admin`** : tout, y compris l'onglet **Paramètres** (gestion des comptes/rôles **et** de la liste des opérateurs de stock du soir) et — comme `commerce` — l'onglet **Produits** (création/modification/suppression de produits, familles/variétés/conditionnements/suremballages).
- **`production`** : saisie du stock du soir (onglet **Stock du soir**, ex-« Production ») ; peut aussi réactiver un produit inactif existant depuis cet onglet (modifie uniquement le champ `actif`) — ne peut pas créer de nouveau produit, ni le supprimer, ni modifier ses autres champs (famille, variété...). **N'a pas accès aux prix d'achat** : l'onglet Prix d'achat lui est entièrement masqué (nav caché), et partout ailleurs où un prix serait normalement affiché (colonne Prix d'achat des onglets Produits/Commerce, détail des achats du jour, récapitulatif de l'onglet Achats, export de sauvegarde Excel) la valeur est remplacée par « — » — voir `peutVoirPrix()`. **Limite connue** : ceci masque les prix côté interface, mais les règles Firestore autorisent la lecture de la collection `produits` entière (`allow read: if connecte();`) à tous les rôles connectés — Firestore ne permet pas de restreindre la lecture à certains champs d'un document. Un utilisateur `production` techniquement curieux pourrait donc encore lire `prixAchatDefaut`/`prixAchatUnite` via un appel direct au SDK/API Firestore, en contournant l'interface. Pour une étanchéité complète il faudrait déplacer les prix dans une collection séparée avec sa propre règle de lecture restreinte à `commerce`/`admin` — non fait à ce stade (changement de modèle de données plus large), accepté comme limite pour une petite équipe de confiance.
- **`commerce`** : onglets **Achats** (entrées de marchandise), **Commerce** (ventes/réservations du jour, par commercial + validation du stock du soir), **Produits** (création/modification/suppression complète des produits — désignation, famille/variété/conditionnement/suremballage, prix d'achat/unité, actif — **et** gestion des listes de référence dont ces quatre champs sont tirés) et **Prix d'achat** (prix par défaut + actif/inactif d'un produit existant, en plus rapide/ciblé que l'onglet Produits). Le catalogue produit reste partagé entre tous les commerciaux (pas de filtrage), mais chaque commercial (Nadine, Julien, Flo, Mickael, Stéphanie...) saisit ses propres ventes et réservations du jour dans son propre sous-onglet Commerce — un compte `commerce` ne peut écrire que le document `commerce` dont le champ `commercial` correspond à son propre email (règle Firestore), l'admin pouvant écrire n'importe quel document pour correction. Seul le bouton « Supprimer tous les produits » (suppression en masse de tout le catalogue) reste réservé à l'admin, par choix — sécurité imposée uniquement par l'interface (masquée), pas par les règles Firestore (qui autorisent `commerce` à supprimer un produit individuellement, comme depuis l'onglet Produits).
- **`viewer`** : lecture seule partout (rôle à assigner explicitement si une personne doit consulter sans saisir).
- **`aucun`** : rôle par défaut si aucun document `users/{uid}` n'existe (auto-créé à la première connexion). Ne donne accès à rien : l'écran « Accès non autorisé » s'affiche à la place de l'application tant que l'administrateur n'a pas changé ce rôle. Seules les personnes avec un rôle explicitement attribué voient l'application.

Un compte ne peut pas changer son propre rôle (sécurité anti-blocage, même règle que paloxs). Création de compte = toujours via la console Firebase (pas de self-signup) ; l'admin assigne ensuite le rôle depuis l'onglet **Paramètres > Comptes** de l'application.

## Onglets de l'application

- **Stock du soir** (onglet nommé « Production » jusqu'à un renommage récent — `vue`/fonctions internes encore appelées `production`/`rendreProduction()` par compatibilité) : le tableau du jour (Produit/Haut/Bas/Total, groupé par famille), la recherche/filtre et l'export **« Exporter le stock du soir (.xlsx) »** restent **toujours visibles**, quel que soit le rôle et qu'une session de comptage soit ouverte ou non. Le bouton **« Ajouter »** (réactiver un produit inactif) fait exception : il n'apparaît que **pendant une session de comptage active** (`sessionStockSoir` non nul) — réactiver un produit n'a de sens qu'en train de réaliser le stock, pas sur l'écran de démarrage/consultation ; si une session se termine pendant que la liste des inactifs était ouverte, elle se referme automatiquement. Ce qui a changé : la saisie fonctionne désormais par **session de comptage** plutôt qu'un enregistrement au blocage de chaque champ. L'écran de démarrage se limite d'abord à un unique bouton **« Démarrer un stock du soir »** ; cliquer dessus révèle le formulaire (`ouvrirFormulaireDemarrage()`/`fermerFormulaireDemarrage()`, état local `formulaireDemarrageOuvert`, non persisté) demandant : la date (aujourd'hui, affichée en lecture seule — le reste de l'app suppose une saisie du jour même, pas de comptage a posteriori pour une autre date), l'heure du contrôle (pré-remplie à l'heure actuelle, modifiable), le côté (**Stock Haut**, **Stock Bas**, ou **Stock Haut + Bas** pour saisir les deux colonnes dans la même session), et l'**opérateur** réalisant le contrôle (liste choisie parmi `parametres/operateurs`, gérée par l'admin — pas un compte de connexion). Une fois démarrée (`demarrerStockSoir()`), la ou les colonnes du tableau correspondant au côté choisi deviennent des champs de saisie (l'autre colonne, s'il y en a une, reste en lecture seule, affichant ce qui est déjà enregistré) ; la colonne **Total** continue d'additionner en direct la valeur en cours de saisie et la valeur déjà enregistrée pour l'**autre** côté quand un seul des deux est édité (si un autre opérateur a déjà fait l'autre) — **cumul immédiat des deux côtés**, sans attendre que les deux soient faits par la même personne. En mode **Stock Haut + Bas**, `saisieSessionEnCours` porte les deux valeurs par produit (`{ haut, bas }`, chacune une chaîne éditable indépendamment) plutôt qu'une seule. **Comportement différent de « Haut seul »/« Bas seul » à l'enregistrement** : ces deux derniers réécrivent tous les produits actifs (0 si non saisi, voir plus bas), alors que **« Haut + Bas » ne touche que les produits où au moins un des deux côtés a été saisi, et n'écrase que le côté effectivement retapé pour chacun** — l'autre côté d'un même produit garde sa valeur existante s'il n'a pas été retapé dans cette session groupée, pour ne jamais écraser une donnée par erreur. Décision explicite de l'utilisateur (« je ne veux pas que les données soient écrasées »), à la différence du mode mono-côté où le remplissage à 0 est volontaire. Comme avant, chaque champ accepte une **addition tapée directement** (ex. `12+8+5`, sommée par `sommerExpression()`). Contrairement à l'ancien modèle, **rien n'est enregistré au fur et à mesure** : les valeurs sont gardées en mémoire locale (`saisieSessionEnCours`) et ne sont écrites dans Firestore qu'au clic sur **« Terminer et enregistrer »** (`terminerStockSoir()`, écriture groupée par lot/`batch()`, portant le côté/opérateur/heure de cette session ; un indicateur `terminaisonEnCours` désactive les boutons Terminer/Annuler pendant l'écriture pour éviter un double clic). **Un produit actif non renseigné dans la session est écrit à 0** pour le ou les côtés en cours (pas laissé inchangé) : la session représente l'inventaire complet des produits actifs pour ce ou ces côtés, donc l'absence de saisie signifie « rien constaté », et non « valeur d'une session précédente du même jour à conserver » — sans ce comportement, un produit compté à une valeur non nulle lors d'un premier passage puis oublié lors d'un second passage du même côté le même jour aurait gardé l'ancienne valeur alors qu'il n'a pas été retrouvé lors du second comptage. Seuls les produits explicitement saisis génèrent une ligne dans l'Historique (`enregistrerTransaction`), pour ne pas noyer le journal de centaines de « 0 ». Un bouton **« Annuler »** abandonne la session (avec confirmation si des valeurs ont déjà été saisies) sans rien écrire. Au-dessus du formulaire « Démarrer un stock du soir », une section **« Stock en cours »** (visible seulement s'il y a au moins une session en cours, tous opérateurs confondus) liste chaque session non terminée du jour — date/côté/opérateur, statut « En cours », bouton **« Reprendre le stock en cours »** (`reprendreStockEnCours()`) — alimentée par la collection `brouillonsStockSoir` (voir plus haut), pour retrouver une session interrompue par la fermeture de l'onglet ou pour voir qu'un autre opérateur a déjà une session ouverte sur ce côté avant d'en démarrer une nouvelle. L'écran « Démarrer un stock du soir » affiche aussi, pour Stock Haut et Stock Bas séparément, l'état du jour (« Enregistré à HH:MM par [opérateur] » ou « Pas encore enregistré aujourd'hui », via `saisieExistanteCote()`) avec un bouton **« Modifier le stock enregistré »** (`modifierStockSoir()`, visible seulement si une saisie existe pour ce côté aujourd'hui et pour les rôles autorisés à saisir) : contrairement à « Démarrer » qui repart d'une session vierge (tout produit non retouché est mis à 0, voir plus bas), « Modifier » relance une session pré-remplie avec les valeurs actuellement enregistrées de ce côté pour tous les produits actifs — un produit non retouché pendant cette édition garde donc sa valeur existante (elle est déjà dans le brouillon local), seuls les produits explicitement changés sont modifiés. En bas de l'onglet, section **« Consulter un stock antérieur »** : un sélecteur de date (borné par la limite de rétention si elle est configurée, voir `parametres/historique` plus haut) et un bouton **« Consulter »** (`consulterStockDate()`) affichent, en lecture seule, le détail Produit/Haut/Bas/Total enregistré pour cette date (requête ponctuelle `saisieStock.where('date','==', dateChoisie)`, pas un `onSnapshot` — pas besoin de temps réel sur une consultation historique), avec les valeurs telles qu'enregistrées à l'époque (pas recalculées), y compris pour un produit renommé/supprimé depuis. Un bouton **« Supprimer ce stock du soir »** (`supprimerStockDate()`, réservé à l'admin, avec confirmation) apparaît sous le résultat s'il y a au moins une ligne pour cette date, et supprime définitivement tous les `saisieStock` de cette date (utile pour une saisie erronée à refaire de zéro — fonctionne aussi bien pour le jour courant que pour un jour passé, puisque le sélecteur de date accepte jusqu'à aujourd'hui). **Limite connue** : la saisie en cours n'est pas persistée avant la fin de la session — fermer l'onglet/le navigateur avant de cliquer sur « Terminer » perd les valeurs non enregistrées de cette session (pas de brouillon auto-sauvegardé). Important : cette saisie n'impacte jamais directement le "dernier stock connu" utilisé par le Commerce — elle passe par la validation (voir onglet Commerce) avant de compter dans le stock réel, qui affiche désormais l'opérateur et l'heure de chaque côté en info-bulle (`title`) sur les colonnes Haut/Bas de la file d'attente.
- **Achats** : onglet de **consultation uniquement** — recherche + récapitulatif de tous les achats (une ligne par produit de chaque livraison), avec bouton **« Modifier »** (rouvre la modale d'achat pré-remplie, voir plus bas) et **« Suppr. »** par ligne (agit sur la livraison entière), réservés au rôle `commerce`. La colonne Prix d'achat du récapitulatif (et sa colonne équivalente dans le PDF) est entièrement omise, pas seulement masquée par un tiret, pour le rôle `production` (voir `peutVoirPrix()`). Bouton **« Générer PDF récapitulatif »** (`exporterAchatsPDF()`) : pour un rôle ayant accès au prix, demande d'abord (via `confirm()`) d'inclure ou non les prix dans le PDF (la production, qui n'y a jamais accès, ne voit pas cette question) ; construit ensuite une vue imprimable (respecte la recherche en cours) dans une zone dédiée (`#zoneImpression`, partagée avec l'export PDF du Stock du soir, visible seulement en impression via `@media print`) et déclenche `window.print()` — orientation **paysage** par défaut (`@page { size: landscape; }`) — l'utilisateur choisit « Enregistrer au format PDF » comme imprimante ; pas de dépendance PDF supplémentaire côté client, sur le même principe que l'export CSV déjà présent ailleurs. La **saisie** d'un nouvel achat ne se fait plus depuis cet onglet : elle passe par une **modale partagée** (`#modalAchat`, en dehors des `.vue` pour rester au-dessus de n'importe quel onglet), ouverte soit depuis le bouton **« + »** de la colonne Achats de l'onglet Commerce (`ouvrirModalAchat(nomProduit)`, avec ce produit préselectionné sur la première ligne — d'autres lignes/produits peuvent être ajoutées comme avant), soit depuis « Modifier » sur une ligne du récapitulatif (`chargerAchatPourEdition()`). La modale reprend telle quelle la logique historique du formulaire (fournisseur, date, **date de livraison prévue** (optionnelle), lignes produit/quantité/prix d'achat/heure de départ/transport = Ramasse ou nom de transporteur avec autocomplétion sur l'historique, ajout/retrait de ligne) — seul le fournisseur n'accepte plus de saisie libre : il se choisit désormais dans la liste de référence `referentiels.fournisseurs` (gérée depuis l'onglet Produits, voir plus bas), unie aux fournisseurs déjà présents dans l'historique des achats pour ne rien perdre des livraisons antérieures à cette liste. Écriture réservée au rôle `commerce`, visible en lecture par tous.
- **Commerce** : sous-onglets **Global** (agrégat en lecture seule, tous commerciaux confondus) et un sous-onglet par commercial (comptes ayant le rôle `commerce`, listés depuis `users`, libellé dérivé du préfixe de leur email). Un compte `commerce` arrive par défaut sur son propre sous-onglet ; un admin peut consulter/corriger n'importe quel sous-onglet. Pour chaque produit actif : **prix d'achat** par défaut (lecture seule, `produits.prixAchatDefaut`), **stock initial** = dernier stock connu (valeur en évidence + date sur une ligne séparée, plus discrète), achats du jour (calculés depuis la collection `achats`, lecture seule ici, avec un bouton **« + »** à côté qui ouvre la modale d'achat — `ouvrirModalAchat()`, voir onglet Achats — pré-remplie avec ce produit, réservé au rôle `commerce`), ventes du jour et réservations (quantité promise à un client, pas encore livrée — **réinitialisées chaque jour comme les ventes**, saisies par commercial), **stock réel** = stock initial + achats − Σventes(tous commerciaux), et **stock disponible** = stock réel − Σréservations(tous commerciaux) (recalculés en direct, toujours sur les totaux tous commerciaux confondus, y compris dans les sous-onglets individuels — les ventes/réservations d'un commercial déduisent donc bien le stock réel/disponible vu par tous les autres). Dans le sous-onglet Global les champs ventes/réservations sont en lecture seule (totaux) ; dans un sous-onglet commercial ils sont éditables (uniquement par ce commercial ou par l'admin) et ne portent que la valeur de ce commercial pour la journée. Un bouton **▸ Détail** par produit déplie une ligne listant les achats du jour (fournisseur, prix, heure, transport) ainsi que la ventilation ventes/réservations par commercial. En dessous, section **Stock du soir à valider** : liste des saisies de production pas encore importées (`saisieStock.importe == false`), regroupées par **session de comptage** (date + attribution Haut + attribution Bas, via `cleSessionValidation()`/`libelleSessionValidation()` — une session « Haut + Bas » a la même attribution des deux côtés et forme donc un seul groupe) avec un bouton **« Valider cette session »** par groupe en plus du bouton par ligne et du bouton global **« Tout valider et importer »** — la validation copie la valeur dans `dernierStock` et marque l'entrée comme importée (`validerStock()`, inchangé, accepte n'importe quel sous-ensemble de lignes).

Plus bas, section **Clôture de la journée** (`#carteClotureJournee`, visible pour `commerce`/`admin`) : une fois le stock du soir du jour validé (donc reflété dans `dernierStock`, le stock initial de demain), les achats et ventes/réservations **déjà comptés aujourd'hui** compteraient une seconde fois si on les laissait dans le calcul du stock réel/disponible pour le reste de la journée. Le bouton **« Clôturer la journée »** (`cloturerJournee()`) déclenche d'abord `exporterSauvegardeExcel()` (sauvegarde complète existante, non bloquante), puis écrit `clotures/{date}` = `{ date, heure: serverTimestamp(), responsable }`. **Aucun document `achats`/`commerce` n'est supprimé ni modifié** — la clôture pose seulement un seuil de temps : `recalculerAchatsDuJour()`/`recalculerCommerceDuJour()` (appelées après chaque mise à jour du cache brut `achatsDocsAujourdhui`/`commerceDocsAujourdhui` **ou** de `clotureAujourdhui`, pour rester à jour sans réinterroger Firestore) excluent du calcul du stock réel toute ligne dont `horodatage` est antérieur ou égal à l'heure de clôture — les achats/ventes déjà existants restent pleinement consultables dans leurs onglets et dans l'Historique, seul le total "aujourd'hui" utilisé par la formule de stock repart de zéro à partir de ce seuil. Reclôturer plus tard dans la journée déplace simplement ce seuil plus loin.
- **Produits** (admin + commerce ; visible en lecture par tous les rôles connectés, comme les autres onglets) : formulaire de création — désignation, puis cinq listes déroulantes **Famille / Variété / Origine / Conditionnement / Suremballage**. Famille, Origine, Conditionnement et Suremballage sont alimentées par l'union des valeurs déjà utilisées dans les produits existants et des listes de référence. **Variété dépend de la Famille choisie** (cascading select, recalculé à chaque changement de Famille via `rendreSelectVariete()`) : elle ne propose que les variétés rattachées à cette famille dans les référentiels, plus celles déjà utilisées par un produit existant de cette même famille. Le champ **Désignation** se construit automatiquement (`composerDesignation()`, appelée par `recalculerDesignationAuto()`) par rapprochement de `[Variété] + [Origine] + [Conditionnement] + [Suremballage]` (la famille n'entre volontairement pas dans ce calcul) dès qu'une des listes change, tout en restant modifiable à la main avant validation. En dessous, tableau de tous les produits (désignation, famille, variété, origine, conditionnement, suremballage, actif, suppression individuelle — **sans le prix ni l'unité**, volontairement retirés de cet onglet et laissés au seul onglet Prix d'achat). Les 5 champs de taxonomie s'affichent en texte simple (plus lisible) tant qu'une ligne n'est pas explicitement passée en édition via un bouton **« Modifier »** — celui-ci fait alors apparaître les listes déroulantes à la place, ainsi qu'un bouton **« Enregistrer »** (et « Annuler ») qui remplacent « Modifier »/« Suppr. » ; la valeur n'est écrite qu'au clic sur « Enregistrer », jamais au simple changement de sélection (`produitEnEdition` ne retient qu'une ligne en édition à la fois). **Enregistrer un changement recalcule aussi la désignation** (via `composerDesignation()`) et l'écrit sur le même document produit (même id Firestore, seul le champ `nom` change) : si la désignation change, une confirmation explicite prévient que le "dernier stock connu" (`dernierStock/main`) est reporté automatiquement sous le nouveau nom, mais que l'historique déjà enregistré (`saisieStock`, `commerce`, `achats`, `transactions` — qui stockent tous le nom du produit en toutes lettres, pas une référence à son id) reste associé à l'ancien nom et n'est pas migré. Une désignation qui entrerait en collision avec celle d'un autre produit existant bloque l'enregistrement. Le statut Actif reste un bouton à bascule toujours cliquable, indépendamment de ce mode d'édition. Seul le bouton **« Supprimer tous les produits »** (vidage complet du catalogue) reste réservé à l'admin, masqué en interface pour `commerce`. Plus bas, section **Listes de référence** (visible/modifiable par admin et commerce, comme le reste de l'onglet) : une carte **Famille & variétés** où chaque famille liste directement ses propres variétés en dessous (avec son propre bouton **« + Nouvelle variété »**, qui rattache la nouvelle valeur à cette famille) — supprimer une famille supprime aussi ses variétés associées (évite des variétés orphelines) — puis quatre cartes simples Origine / Conditionnement / Suremballage / **Fournisseur** (valeurs à plat, sans lien). La carte Fournisseur alimente la liste déroulante Fournisseur de la modale de saisie d'achat (voir onglet Achats) — placée ici plutôt que dans l'onglet Achats à la demande explicite de l'utilisateur, pour garder tous les référentiels au même endroit. Chaque carte a un bouton **« + Nouvelle... »** qui fait apparaître une ligne de saisie vide, confirmée (écriture Firestore) à la perte de focus si non vide. **Il n'est pas possible de créer une nouvelle valeur de famille/variété/origine/conditionnement/suremballage/fournisseur directement depuis le formulaire de création de produit ou d'achat** (pas d'option « + Nouvelle... » sur les 5 listes déroulantes elles-mêmes) — cela passe obligatoirement par cette section dédiée, pour garder la création de référentiels comme un geste délibéré.
- **Prix d'achat** : vue allégée de la même liste de produits (actifs ou non), centrée sur leur prix d'achat par défaut (affiché/saisi en €) et son unité (**Colis** ou **Kilo**) plus leur statut actif/inactif (saisonnalité) — plus rapide à parcourir pour un ajustement quotidien de prix que l'onglet Produits complet, et c'est le **seul** endroit où le prix/l'unité sont affichés parmi les onglets de gestion produit. Modifiable par le rôle `commerce` (et admin) — les autres colonnes (famille, variété, origine, conditionnement, suremballage) y sont affichées en lecture seule. Dans l'onglet Commerce, la colonne Prix d'achat affiche la même valeur avec son unité (ex : « 2 € / colis »). Le tableau de produits de l'onglet Produits et celui de Prix d'achat partagent les fonctions `champPrixAchat()`/`champUniteAchat()`.
- **Historique** : journal de toutes les actions (stock du soir, achats, ventes, prix, activation/désactivation produit), recherche libre, export CSV, suppression réservée à l'admin. Un bouton **« Exporter sauvegarde Excel (.xlsx) »** génère en plus un classeur complet (un onglet par collection : Produits, Stock du soir, Ventes, Achats, Historique) via la bibliothèque SheetJS chargée en CDN — pensé comme sauvegarde locale, accessible à tous les rôles.
- **Paramètres** (admin uniquement) : section **Opérateurs** — liste des personnes réalisant les contrôles de stock du soir (`parametres/operateurs`), même interface que les cartes de Listes de référence (ligne + lien « supprimer », bouton « + Nouvel opérateur » qui révèle une ligne de saisie vide). Puis section **Historique du stock du soir** — un champ numérique pour le nombre de jours de saisies à conserver (`joursConservationStockSoir`, vide = illimité) et un bouton « Enregistrer » (voir `parametres/historique` plus haut). Puis gestion des rôles par compte — la gestion des produits et des listes de référence (autrefois envisagée ici) vit dans l'onglet **Produits**, partagé avec `commerce`.

## Style / thème

Même identité que l'app paloxs (cohérence entre les deux outils) : palette `--copper: #963E88`, vague dégradée (`--wave-1: #B23C92` → `--wave-2: #5B2A66`) sous l'en-tête et la carte de connexion, polices Fraunces (titres) / Inter (texte) / IBM Plex Mono (chiffres). Icône caisse/palox (SVG inline) sur l'écran de connexion, plutôt qu'oignon/échalote (déjà utilisé par l'app paloxs) — pour distinguer visuellement les deux outils tout en gardant la même famille graphique.

## Origine des données produits

Le schéma produit garde en tête un export possible du catalogue de l'entreprise (fiche article : Code, EAN13, Désignation, Famille, Variété, Origine, Conditionnement, Calibre, Catégorie, PCB Vte, Suremballage, Label, Actif...), mais l'app ne conserve volontairement qu'un sous-ensemble de ces champs, jugés pertinents pour l'usage quotidien et pour la création manuelle depuis l'onglet **Produits** (pas de catalogue pré-rempli — chaque produit est créé par l'admin ou un compte `commerce`) :

- `nom` (= Désignation complète de l'article — **composée automatiquement** par rapprochement de `variete` + `origine` + `conditionnement` + `suremballage` (la famille n'entre pas dans ce calcul) à la création comme à la modification, tout en restant modifiable à la main avant validation ; voir `composerDesignation()`. Modifier un produit recalcule et réécrit `nom` sur le même document (l'id Firestore, dérivé du nom à la création, ne change pas) ; l'historique (`saisieStock`/`commerce`/`achats`/`transactions`, qui stockent le nom en toutes lettres) n'est pas retroactivement mis à jour, seul `dernierStock/main` est reporté sous le nouveau nom)
- `famille` (ex : Oignon, Mini légumes)
- `variete` (ex : Oignon de Roscoff, Mini carotte)
- `origine` (ex : France, Espagne — liste de référence à plat, indépendante de la famille/variété)
- `conditionnement` (ex : Sac 5kg, Barquette 250g, Tresse fourreau 1kg)
- `suremballage` (ex : Palox, Carton, Caisse, Meuble, Coffret, Barquette, Sachet, Sans suremballage)
- `actif`, `prixAchatDefaut`, `prixAchatUnite`, `ordre`

Champs volontairement **non conservés** : Code article, EAN13, Calibre, Catégorie, PCB Vte, Label, Préparation, Complément, Controle légumière, Marque, Poids U. Vte. Le champ `nom` (désignation) sert de clé d'unicité fonctionnelle.

`famille`, `variete`, `origine`, `conditionnement` et `suremballage` sont **gérés par l'admin et le commerce, sans liste figée dans le code**, depuis l'onglet Produits > section Listes de référence. **Chaque variété est rattachée à une famille** (`{ nom, famille }` dans `referentiels/main.varietes`) : elle se crée directement sous la famille concernée (bouton « + Nouvelle variété » propre à chaque famille), pas comme une liste de variétés indépendante — le menu Variété du formulaire de création de produit filtre donc ses options selon la Famille déjà choisie. Familles, origines, conditionnements et suremballages restent des listes à plat, indépendantes les unes des autres (un bouton « + Nouvelle... » par carte qui révèle une ligne de saisie vide en bas de liste, confirmée à la perte de focus si non vide, abandonnée sinon). Les 5 listes déroulantes du formulaire de création de produit lisent l'union de ces valeurs et de celles déjà utilisées sur des produits existants (pour ne rien perdre de l'historique antérieur à cette collection), mais n'offrent elles-mêmes plus de moyen d'ajouter une nouvelle valeur à la volée (l'option « + Nouvelle... » directement sur ces 5 listes déroulantes, présente dans une version antérieure, a été retirée à la demande explicite de l'utilisateur : la création de valeurs de référence doit rester un geste délibéré depuis la section dédiée, pas un sous-produit de la création d'un article). Aucun catalogue n'est pré-chargé (`Produits_initial.json` est un tableau vide, gardé comme documentation du format) ; la liste se construit produit par produit depuis l'app. Premières familles prévues : Oignon (Roscoff AOP), puis Mini légumes. Extension prévue à d'autres familles et, à terme, aux autres commerciaux (Nadine, Julien, Flo, Mickael, Stéphanie).

## Pour continuer le développement

Ouvrir ce dossier avec Claude Code (ou coller ce fichier en contexte) suffit à comprendre l'architecture sans relire tout `index.html`. Toujours valider la syntaxe JS après édition (`node --check` sur le contenu du `<script>` inline) avant de committer/pousser. Évolution déjà anticipée dans le modèle de données : réimport ponctuel vers Excel si besoin — les collections `saisieStock`/`commerce` s'exportent facilement (requête par plage de dates → CSV), sur le même principe que l'export CSV déjà présent dans l'onglet Historique.

Note sur la migration `commerce` (doc par produit+jour → doc par produit+jour+commercial) : les anciens documents `commerce` écrits avant ce changement n'ont pas de champ `commercial` — ils ne remontent donc dans aucun sous-onglet individuel (seulement dans un total Global s'ils sont un jour ré-agrégés manuellement) et n'ont pas de `reservations` (ce champ vivait auparavant sur `produits`). Aucune migration automatique n'a été faite ; à surveiller si un historique `commerce` antérieur à ce changement doit être ré-exploité.
